## 1. 估算历史与版本（FR-1.1、1.8、2.5）

数据模型见 `docs/概要设计说明.md` §4（`estimation.db` 单表 `estimation_history`，`version_group + version_no` 为版本键）。

**API**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/history?query=&limit=50&offset=0` | 列表（时间倒序），query 对 title/source_name 做 LIKE |
| GET | `/api/history/{id}` | 详情（含解析后的明细数组） |
| DELETE | `/api/history/{id}` | 删除单条（不删成品文件） |
| GET | `/api/history/{id}/group` | 同组各版本（重开时提示「这是第 N 版」） |

**落库接线点**：`do_POST /api/generate` 成功分支内、进度置 100 之后写入一条历史（items/method/title/sid/summary/recalc_mode）；
请求可选 `reopen_group`（重开沿用版本组并自增）、`fee_version`（费率口径），缺省行为不变。
**落库失败只记日志、不影响生成响应**。明细体积 >1MB 拒绝；`estimation.db` 打不开时历史功能禁用但不阻塞估算。

**前端流程**

```
重开 → GET /api/history/{id} → 确认弹层（版本功能点数/生成时间）
→ items = 历史明细，标题置为历史标题 → 复核页修订
→ /api/generate 带 reopen_group=<原组> → version_no+1
另存为 = 重开后改标题、不传 reopen_group → 新版本组
```

`localStorage('last_history_id')` 支持刷新后提示「恢复上次估算」（FR-1.8）。
**Diff 基础**：`version_group+version_no` 定位任意相邻版本，`items_json` 每条带稳定 `seq`；
按 `(system+desc)` 归一化键输出 added/removed/changed，成品见 `/api/history/diff` 与结果页对比面板。
**敏感性**：明细可能含客户业务信息，库文件不参与任何上传，诊断包排除该库。

## 2. 接口入参校验（FR-5.3）

`scripts/validators.py`（dataclass，零依赖）：

| 校验器 | 要点 |
|---|---|
| RecognizeIn | name 非空、b64 合法且 ≤50MB |
| GenerateIn | items 非空；每条 type/reuse/modify ∈ 枚举；method ∈ 枚举；brand_color 匹配 `#RRGGBB`；gb_state 数值合法 |
| RulesDoc | patterns 非空且可编译、priority 0–999、enabled 布尔 |
| RatesDoc | 复用 `gb_engine.rates_ok` |

各 POST 入口统一 `check(payload, ValidatorX)`，失败返回 `400 {ok:false,msg,field}`（field 形如 `items[3].type`）并写结构化日志。
**原则：只收紧明显非法输入，不改变任何现有合法行为**（由测试套件保证无回归）。

## 3. 日志与诊断包（FR-5.4）

- `scripts/slog.py`：`slog(level, module, event, **kv)` → JSON 行追加 `WE_DATA/logs/server.jsonl`（ts/level/module/event/duration_ms/自定义）；启动、识别、生成、规则/费率保存、备份、诊断包导出等关键事件埋点；保留 print 以兼容既有 grep
- `GET /api/diag` → zip（`diag_<时间戳>.zip`）：近 7 天日志 + **脱敏配置**（剔除 api_key/token）+ version.json（应用版本/schema_ver/Python 版本/路由清单）
- **不含** `uploads/`、`generated/`（可能含用户业务数据）

## 4. 备份与迁移（FR-5.6）

`scripts/datakeeper.py`：

- **启动备份**：复制 `pert.db`、`recognition_rules.json`、`rates_versions.json` 到 `WE_DATA/backups/<ts>/`，保留最近 7 份
- **schema 版本 + 迁移**：`WE_DATA/schema_ver`（整数）+ 幂等迁移函数表，启动时逐级执行并写回（首版 1，框架就绪）
- **导出/导入**：`GET /api/data/export` → zip（数据库 + 三个 json + schema_ver）；`POST /api/data/import` 校验版本不高于当前 → 自动备份 → 解包覆盖 → 返回清单

**关键决策**

1. **UI 驱动用 CDP 直连无头 Chrome，不引入 Playwright**（零新增依赖，5 个稳定套件零重写风险）；若将来切换，用 `playwright-core + channel:'chrome'` 不下载浏览器
2. **双层运行时**：node（编排 + UI）+ python（单测/冒烟，仅标准库，无需 venv）
3. **隔离**：每套件独立 `WE_DATA=临时目录`，端口段 API 8032 起、CDP 9334 起；起前查端口占用、退后强杀子树（防双监听孤儿）
4. **夹具**：`data/testdocs/`（入库），夹具路径必须用**绝对路径** —— 相对路径会被 Chrome 按自身 cwd 解析，无效 File 让渲染器整体冻结（T01079 根因）
5. **报告**：console 实时 PASS/FAIL + `logs/test_report_<时间戳>.md`；任一失败退出码 1
6. **需要桌面的套件门住而非跑挂**（T03955）：S17 依赖可交互窗口站（原生 TaskDialog 要靠 UIA 找控件、BM_CLICK 点按钮），非 Windows / 未装 `dev-shell/node_modules/electron` / 会话无 `explorer.exe` 时统一 SKIP 并把原因写进报告，不参与判红；`WE_SHELL_TEST=1|0` 可强制跑/跳。它的耗时预算单独放宽到 15min（本机空载 1m37s，多会话并发时退出链会被拖慢，用 300s 默认预算会假红），并同步抬高用例内看门狗
7. **合成点击不作数，以「对话框窗口真没了」为投递判据**（T04475）：`SendMessageTimeout(BM_CLICK)` 返回 TRUE 只说明消息投递成功，TaskDialog 的首按约 1/5~1/3 不会变成主进程收到的决策（空载两批各 15 次，分别吞 5 次与 2 次，合计 7/30；与点击距弹框创建的间隔无关，0ms 与 400ms 都吞，且对话框线程 13~142ms 起就一直在取消息——「等就绪再点」防不住；换鼠标消息 `WM_LBUTTONDOWN/UP` 也吞 8 次 1 次，先抢前台+给焦点是 8 次 0 次，样本太少不足以当成解法）。所以驱动按「补按直到窗口消失，最多三次」（补按实测 0~50ms 内生效），并且**按钮序号按屏幕位置从左到右取**——`EnumChildWindows` 返回的是 z-order，两次调用之间会翻转，按序号补按会点到另一个按钮（实测把 `exit_app` 补成了 `minimize_to_tray`）。主进程侧配一对可观测出口：`askCloseAction` 进/出各落一行 `[close-dialog] shown/resolved`（带 pid），用来把「弹出来了没人点」与「点了没回调」分开
   - **T04505 把三条对照通道量完了，现行打法不换**（2026-11-06 本机空载，`node tests/tools/native_dialog_probe.mjs --modes 0,1,2,3 --rounds 15`，逐轮明细落 `logs/t04505/probe_*.log`）：
     - **BM_CLICK（通道 0）**：当天三批共 30 轮有效，首按吞 1 次 = **1/30（3.3%）**，接住耗时中位 159~184ms、max 290ms。比 T04475 的 7/30 低一个量级——说明吞按率强烈依赖机器负载，**任何一天的 0/N 都不等于「问题消失了」**，补按这条兜底必须留着。
     - **抢前台+给焦点（通道 3）**：先决条件是「真抢到了」——跨进程 `SetForegroundWindow` 会被前台锁挡掉（裸调实测返回 False，那样跑出来的数字只是通道 0 的换皮）；补上 `AllowSetForegroundWindow` + ALT 键解锁 + `AttachThreadInput` 后 `SFW/ATTACH/FOCUS/IS_FOREGROUND` 全 True，15 轮 **0/15 吞按，但接住耗时中位 298ms、max 525ms，比通道 0 慢一倍**，已逼近驱动 700ms 判据窗口。结论：它不是更好的通道，只是当天也没撞上吞按；换成它会把手感从「150ms 接住」拖到「300~500ms」，高负载下反而更容易被判成吞按。
     - **UIA `InvokePattern`（通道 1）与 `LegacyIAccessible.DoDefaultAction`（通道 2）：压根发不出点击，不是「发出去被吞」**。TaskDialog 的按钮在 UIA 里是 `ControlType.Pane`——子树 6 个元素、`ControlType.Button` 0 个、带目标 pattern 的元素 0 个，按文案能命中那个 Pane（`NAMEMATCH=1`）但它没有 pattern，14/14 与 4/4 轮全部 `INVOKE=pattern_unavailable`。本机连 UIA COM 客户端都起不来（`CUIAutomation8`/`CUIAutomation` ProgID 未注册，`0x80040154 REGDB_E_CLASSNOTREG`），只剩 managed 客户端，而 managed 压根没有 `LegacyIAccessiblePattern` 这个类型（`TypeNotFound`）。所以「UIA 通道能把吞按率打到 0」**从未被测出过**，它的前提（拿得到 pattern）在本机不成立；下一个想重试的人先看这条，并记住区分「这个客户端问不出来」与「这个控件不支持」。要真正把 LegacyIAccessible 量出来，得走原生 MSAA `IAccessible::accDoDefaultAction`（不依赖 UIA 客户端），已建派生单。
     - **第二条判据（宽限窗 `GRACE`）实测**：当天唯一那次吞按在 2s 内窗口仍在（`GRACE=open`），补按 92ms 接住——吞掉的那一次不是「销毁排队只是慢」，是真没接住。判据本身不用改，回归仍只按 700ms 内 `IsWindow` 判。
     - 附带修掉的两个测量陷阱：UIA `RootElement` 枚举偶发看不到刚建好的 `#32770`（异常「找不到任何对象」），而弹框在 Win32 侧真实存在并一直挂着 → 之后每轮的 `WM_CLOSE` 都被这道模态吞掉，整批轮次作废；驱动现在 UIA 失败就按 pid+class 退回 `EnumWindows`，探针在 `not_found` 轮补一次清场。复选框在退回路径走 `BM_GETCHECK/BM_SETCHECK`，UIA 独有的文案取证如实标 `uia_unavailable`（红了才对，不许假绿）。
