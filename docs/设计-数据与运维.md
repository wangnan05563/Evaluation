## 1. 估算历史与版本（FR-1.1、1.8、2.5）

数据模型见 `docs/概要设计说明.md` §4（`estimation.db` 单表 `estimation_history`，`version_group + version_no` 为版本键）。

**API**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/history?query=&limit=50&offset=0` | 列表（时间倒序），query 对 title/source_name 做 LIKE |
| GET | `/api/history/{id}` | 详情（含解析后的明细数组） |
| DELETE | `/api/history/{id}` | 删除单条（不删成品文件） |
| GET | `/api/history/{id}/group` | 同组各版本（重开时提示「这是第 N 版」） |

**落库接线点**：`do_POST /api/generate` 成功分支内、进度置 100 之后写入一条历史（items/method/title/sid/summary/recalc_mode）；
请求可选 `reopen_group`（重开沿用版本组并自增）、`fee_version`（费率口径），缺省行为不变。
**落库失败只记日志、不影响生成响应**。明细体积 >1MB 拒绝；`estimation.db` 打不开时历史功能禁用但不阻塞估算。

**前端流程**

```
重开 → GET /api/history/{id} → 确认弹层（版本功能点数/生成时间）
→ items = 历史明细，标题置为历史标题 → 复核页修订
→ /api/generate 带 reopen_group=<原组> → version_no+1
另存为 = 重开后改标题、不传 reopen_group → 新版本组
```

`localStorage('last_history_id')` 支持刷新后提示「恢复上次估算」（FR-1.8）。
**Diff 基础**：`version_group+version_no` 定位任意相邻版本，`items_json` 每条带稳定 `seq`；
按 `(system+desc)` 归一化键输出 added/removed/changed，成品见 `/api/history/diff` 与结果页对比面板。
**敏感性**：明细可能含客户业务信息，库文件不参与任何上传，诊断包排除该库。

## 2. 接口入参校验（FR-5.3）

`scripts/validators.py`（dataclass，零依赖）：

| 校验器 | 要点 |
|---|---|
| RecognizeIn | name 非空、b64 合法且 ≤50MB |
| GenerateIn | items 非空；每条 type/reuse/modify ∈ 枚举；method ∈ 枚举；brand_color 匹配 `#RRGGBB`；gb_state 数值合法 |
| RulesDoc | patterns 非空且可编译、priority 0–999、enabled 布尔 |
| RatesDoc | 复用 `gb_engine.rates_ok` |

各 POST 入口统一 `check(payload, ValidatorX)`，失败返回 `400 {ok:false,msg,field}`（field 形如 `items[3].type`）并写结构化日志。
**原则：只收紧明显非法输入，不改变任何现有合法行为**（由测试套件保证无回归）。

## 3. 日志与诊断包（FR-5.4）

- `scripts/slog.py`：`slog(level, module, event, **kv)` → JSON 行追加 `WE_DATA/logs/server.jsonl`（ts/level/module/event/duration_ms/自定义）；启动、识别、生成、规则/费率保存、备份、诊断包导出等关键事件埋点；保留 print 以兼容既有 grep
- `GET /api/diag` → zip（`diag_<时间戳>.zip`）：近 7 天日志 + **脱敏配置**（剔除 api_key/token）+ version.json（应用版本/schema_ver/Python 版本/路由清单）
- **不含** `uploads/`、`generated/`（可能含用户业务数据）

## 4. 备份与迁移（FR-5.6）

`scripts/datakeeper.py`：

- **启动备份**：复制 `pert.db`、`recognition_rules.json`、`rates_versions.json` 到 `WE_DATA/backups/<ts>/`，保留最近 7 份
- **schema 版本 + 迁移**：`WE_DATA/schema_ver`（整数）+ 幂等迁移函数表，启动时逐级执行并写回（首版 1，框架就绪）
- **导出/导入**：`GET /api/data/export` → zip（数据库 + 三个 json + schema_ver）；`POST /api/data/import` 校验版本不高于当前 → 自动备份 → 解包覆盖 → 返回清单

**关键决策**

1. **UI 驱动用 CDP 直连无头 Chrome，不引入 Playwright**（零新增依赖，5 个稳定套件零重写风险）；若将来切换，用 `playwright-core + channel:'chrome'` 不下载浏览器
2. **双层运行时**：node（编排 + UI）+ python（单测/冒烟，仅标准库，无需 venv）
3. **隔离**：每套件独立 `WE_DATA=临时目录`，端口段 API 8032 起、CDP 9334 起；起前查端口占用、退后强杀子树（防双监听孤儿）
4. **夹具**：`data/testdocs/`（入库），夹具路径必须用**绝对路径** —— 相对路径会被 Chrome 按自身 cwd 解析，无效 File 让渲染器整体冻结（T01079 根因）
5. **报告**：console 实时 PASS/FAIL + `logs/test_report_<时间戳>.md`；任一失败退出码 1
6. **需要桌面的套件门住而非跑挂**（T03955）：S17 依赖可交互窗口站（原生 TaskDialog 要靠 UIA 找控件、BM_CLICK 点按钮），非 Windows / 未装 `dev-shell/node_modules/electron` / 会话无 `explorer.exe` 时统一 SKIP 并把原因写进报告，不参与判红；`WE_SHELL_TEST=1|0` 可强制跑/跳。它的耗时预算单独放宽到 15min（本机空载 1m37s，多会话并发时退出链会被拖慢，用 300s 默认预算会假红），并同步抬高用例内看门狗
7. **合成点击不作数，以「对话框窗口真没了」为投递判据**（T04475）：`SendMessageTimeout(BM_CLICK)` 返回 TRUE 只说明消息投递成功，TaskDialog 的首按约 1/5~1/3 不会变成主进程收到的决策（空载两批各 15 次，分别吞 5 次与 2 次，合计 7/30；与点击距弹框创建的间隔无关，0ms 与 400ms 都吞，且对话框线程 13~142ms 起就一直在取消息——「等就绪再点」防不住；换鼠标消息 `WM_LBUTTONDOWN/UP` 也吞 8 次 1 次，先抢前台+给焦点是 8 次 0 次，样本太少不足以当成解法）。所以驱动按「补按直到窗口消失，最多三次」（补按实测 0~50ms 内生效），并且**按钮序号按屏幕位置从左到右取**——`EnumChildWindows` 返回的是 z-order，两次调用之间会翻转，按序号补按会点到另一个按钮（实测把 `exit_app` 补成了 `minimize_to_tray`）。主进程侧配一对可观测出口：`askCloseAction` 进/出各落一行 `[close-dialog] shown/resolved`（带 pid），用来把「弹出来了没人点」与「点了没回调」分开
   - **T04505 把三条对照通道量完了，现行打法不换**（2026-11-06 本机，用 `node tests/tools/native_dialog_probe.mjs --modes <通道号> --rounds 15` 分通道跑；`--noClickStop` 默认已是 999，好让「发不出点击」的轮次也照样跑满记进报告，不被提前收轮藏掉。分通道跑是必须的：一次把 0,1,2,3 串在一批里，后面的通道会被下面的整批作废陷阱吃掉），逐轮明细落 `logs/t04505/probe_*.log` 与 `logs/t04505/sanity_*.log`；`logs/` 被 gitignore 排除，证据只在这台机器上）：
     - **BM_CLICK（通道 0）**：当天有效 18 轮、首按吞 2 次 = **2/18（11.1%）**，两次都出自单轮 sanity 批次（`sanity_grace.log`、`sanity_env_check.log`，各 1/1），最大的那批 14 轮反而 0 次（`probe_bm_fg_15.log`，接住耗时 min/中位/max = 112/184/290ms）；前一天同机另有 15 轮 2/15（13.3%）、max 655ms（`probe_bm20.log`）。对照 T04475 的 7/30，吞按率强烈依赖机器负载与当天批次——**任何一天的 0/N 都不等于「问题消失了」**，补按这条兜底必须留着。另有一批 15 轮只拿到 1 轮有效数据（`probe_bm_15b.log`，14 轮被 `not_found` 卡死作废），这正是下面那条测量陷阱的现场。
     - **抢前台+给焦点（通道 3）**：先决条件是「真抢到了」——跨进程 `SetForegroundWindow` 会被前台锁挡掉（裸调实测返回 False，那样跑出来的数字只是通道 0 的换皮）；补上 `AllowSetForegroundWindow` + ALT 键解锁 + `AttachThreadInput` 后 `SFW/ATTACH/FOCUS/IS_FOREGROUND` 全 True，批次 14 轮 **0/14 吞按，但接住耗时 min/中位/max = 213/298/525ms，比通道 0 同日的 184ms 慢一倍以上**（`probe_m3_15.log`），max 已逼近驱动 700ms 判据窗口。结论：它不是更好的通道，只是当天也没撞上吞按；换成它会把手感从「150ms 接住」拖到「300~500ms」，高负载下反而更容易被判成吞按。
     - **UIA `InvokePattern`（通道 1）与 `LegacyIAccessible.DoDefaultAction`（通道 2）：压根发不出点击，不是「发出去被吞」**。TaskDialog 的按钮在 UIA 里是 `ControlType.Pane`——子树 6 个元素、`ControlType.Button` 0 个、带目标 pattern 的元素 0 个，按文案能命中那个 Pane（`NAMEMATCH=1`）但它没有 pattern，两条通道累计 24 轮与 12 轮（含 11-05 的批次，通道 1 单批最多 14 轮见 `probe_uia_15c.log`）全部 `INVOKE=pattern_unavailable`，**没有一轮 `INVOKE=sent`**。本机连 UIA COM 客户端都起不来（`CUIAutomation8`/`CUIAutomation` ProgID 未注册，`0x80040154 REGDB_E_CLASSNOTREG`），只剩 managed 客户端，而 managed 压根没有 `LegacyIAccessiblePattern` 这个类型（`TypeNotFound`）。所以「UIA 通道能把吞按率打到 0」**从未被测出过**，它的前提（拿得到 pattern）在本机不成立；下一个想重试的人先看这条，并记住区分「这个客户端问不出来」与「这个控件不支持」。要真正把 LegacyIAccessible 量出来，得走原生 MSAA `IAccessible::accDoDefaultAction`（不依赖 UIA 客户端），已建派生单 T04539。通道 2 想按「每打法 ≥15 次」出数时另踩了一次下面的整批作废陷阱（`probe_lia_15b.log`：连 7 轮全 `not_found`、第 1 轮 `shown=1`，跑到一半手工中止，最后只有 3 次单轮补测拿到 `pattern_unavailable`）。

     - 附带修掉的两个测量陷阱：UIA `RootElement` 枚举偶发看不到刚建好的 `#32770`（异常「找不到任何对象」），而弹框在 Win32 侧真实存在并一直挂着 → 之后每一轮都拿不到新数据，整批轮次作废（**为什么拿不到，见下一条 T04540：不是「WM_CLOSE 被模态吞掉」**）；驱动现在 UIA 失败就按 pid+class 退回 `EnumWindows`，探针在 `not_found` 轮补一次清场。复选框在退回路径走 `BM_GETCHECK/BM_SETCHECK`，UIA 独有的文案取证如实标 `uia_unavailable`（红了才对，不许假绿）。
   - **T04540 把「整批轮次作废」量成了两条独立成因，并修掉了那条真的**（2026-11-06，逐轮明细落 `logs/t04540/`；现场脚本一并留档 `exp1/exp2/exp3.mjs`）：
     - **① 关闭请求压根没送到（这才是主因）**：探针每轮点「最小化到托盘」，主窗 `hide()` 之后 Win32 侧不可见，而不带 `/F` 的 `taskkill` **只给可见顶层窗发 WM_CLOSE**——它在窗口隐藏时是个静默空操作（taskkill 自己照样回 SUCCESS，所以以前没人察觉）。实测 exp3：主窗隐藏后连发两次 taskkill，`[close-dialog] shown` 停在 1、2 不增；同样位置换 `PostMessage(主窗句柄, WM_CLOSE)` 则 1→2、2→3 每轮都弹。后果是**连最健康的 BM_CLICK 通道也只能出第 1 轮数据**（改前实录 `logs/t04540/probe_m0_before_fix_relaunch.log`：第 1 轮有数据，第 2~4 轮全 `not_found` + `shown=0`）。修法：`tests/win_dialog.mjs` 新增 `postCloseToMainWindow(pid)`（`EnumWindows` 收 `Chrome_WidgetWin_1` 句柄后逐个投 `0x0010`，刻意不看返回值，判据仍是本进程自己的 shown 行），探针的每轮关闭请求改走它——换完 **15 轮 15/15 全部产出新弹框**、无新弹框 0 轮（`probe_m0_fix.log`，当天 0/15 吞按，与②无关，别拿它当「吞按问题消失」）。`requestClose`（taskkill）**保持不动**，S17 与装包烟测继续用它：真实用户的 X 只发生在可见窗口上，那里两者等价，且 taskkill 更贴近产品入口。
     - **② 弹框停在 await 把后续轮次按住**：`askCloseAction` 还没返回时 `main.js` 的 `win.__closeBusy` 门会挡掉之后每一次关闭请求。**工单原来怀疑的「taskkill 不带 /F 会把 WM_CLOSE 投给所有顶层窗口、因而吃掉上一轮的弹框」不成立**——exp1 实测：模态框还挂着时连发第二、第三次 taskkill，`MODAL_COUNT` 恒为 1、`resolved` 恒为 0、主窗一直可见，弹框既没被销毁也没收到回调，它是自己挂在那儿的（exp2 进一步显示这期间每轮驱动报 `not_found` + `shown=0`，形状和①一模一样，光看驱动输出分不出来）。修法：每轮收尾按「本进程 shown 行数 − resolved 行数」查有没有停在 await 的弹框，有就用 BM_CLICK 清掉，清场动作不计入任何通道的吞按率。这条链单独端到端跑通过（exp4：挂着弹框时第二次 WM_CLOSE 确实不弹新框、parked 判据恰好为 1、清场第 1 次按就被吞且第 2 次 88ms 接住、`resolved` 落地后再投 WM_CLOSE 才又弹出新框）——**清场必须带重试**，单次 BM_CLICK 连「把挂着的框收掉」这件事都防不住。
     - **兜底 + 记账口径**：`--relaunch`（默认 3）——连续 3 轮本进程不再弹新框就 `killTree` 换新实例接着跑剩余轮次，`--noClear 1` 可故意不清场，用来单独验证这条接管链。判据用 **shown 行数**而不是「驱动 not_found」：挂着上一轮旧弹框时驱动照样报 found（找到的就是那个旧的），两种形状都只有 shown=0 能兜住。汇总与小结一律**按实例分行**（行首带 pid、起始轮次、「中途重启接管」），不把两台实例的数据混成同一个吞按率——否则「换了个进程」这件事就被藏掉了。

辅助校验：`python tests/i18n_check.py`（双语 key 对齐 + JSON 重复键检测）、`python tests/refactor_guard.py <基线.json>`（API 响应归一化对拍）、`python scripts/generate_xlsx.py --verify`（金标准）。
