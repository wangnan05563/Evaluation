# GitHub 同类产品调研与工作量评估助手优化需求

> 调研日期：2026-11-21　数据截止：2026-11-21　适用产品：工作量评估助手 0.1.20261119-004  
> 调研对象：GitHub 公开仓库与产品页；星标数仅代表社区热度，不代表商业采用或产品质量。

## 摘要

**核心判断：在本次筛选的 GitHub 公开仓库中，尚未出现成熟的“需求文档 → IFPUG 功能点 → 企业造价表”一体化开源产品。** 直接同类多为表格、桌面计算器、单点 Web 工具或 AI Skill；真正成熟的能力分布在项目组合、时间与成本、实时协作、概率估算四个相邻赛道。

工作量评估助手的差异化护城河是**本地离线、文档自动识别、逐条可审计、母版保真出表**。下一阶段不应追逐通用项目管理，而应围绕四个方向做深：**复核效率、审计交付、实际值校准、设计系统与品牌主题**。

建议采用双轨策略：单机离线版继续服务个人评估师与内网用户；新增可选的局域网/私有化工作组版，服务 5–20 人的评审团队。两者共享同一引擎与数据格式，不强制上云。

本次共筛选 18 个代表性仓库，形成 37 项优化需求，其中 P0 14 项、P1 15 项、P2 8 项。P0 聚焦：复核工作台、审计报告中心、稳定功能 ID、实际值闭环、蒙特卡洛预测、数据网格、设计系统与无障碍。

## 一、调研范围与方法

### 1.1 筛选口径

- 方法相关性：IFPUG、NESMA、COSMIC、PERT、COCOMO、软件成本/工作量估算。
- 产品完整度：是否有可运行的界面、数据模型、报告或协作能力，而非纯论文/脚本片段。
- 可借鉴性：在项目组合、时间与成本、实时协作、现代 UI、主题系统上是否提供成熟范式。
- 证据来源：GitHub README、产品页、仓库描述；对关键产品读取 README 原文，不以名称猜测能力。

### 1.2 搜索与筛选

使用 `function point`、`IFPUG`、`functional size measurement`、`software cost estimation`、`effort estimation`、`PERT`、`COCOMO`、`planning poker`、`workload estimation` 等关键词检索，并对项目组合与时间追踪类产品做补充检索。初筛 60+ 仓库，精读 18 个代表性仓库的 README/产品页。

### 1.3 样本结构

- 直接 IFPUG/FPA 工具 8 个：从 Excel 模板、Java Swing、桌面应用、Web 平台到 AI Skill。
- 估算/预测引擎 5 个：PERT、COCOMO、蒙特卡洛、参考类预测、代码度量。
- 项目组合/协作/时间 5 个：OpenProject、Plane、Huly、Kimai、Thunderdome。

> 重要发现：直接 FPA 产品的 GitHub 星标普遍在 0–22 之间，且多为单人维护的工具型项目；这说明品类仍处早期，没有成熟的 UX 基准，必须从相邻赛道借鉴定度。

## 三、当前产品基线

| 维度 | 现状 | 边界与证据 |
|---|---|---|
| 定位 | 本地运行的半自动工作量评估工具：需求文档 → IFPUG 候选 → 人工复核 → 成品 xlsx | 不做全自动无审核出表、云端同步、移动端适配、报价审批流转 |
| 方法 | IFPUG、NESMA 快速估算、PERT 三点估算、GB/T 36964 国标造价、COCOMO II 参考 | PERT 目前为期望值 + 标准差，无置信区间与模拟 |
| 输入 | `.docx` 需求说明书、人工录入、PERT 项目、配置中心费率/母版 | 不支持 PDF/Excel/需求管理平台直接导入 |
| 输出 | 成品 xlsx（母版保真）、PERT 表、CSV/Markdown 摘要、用户故事、GitHub Issues | 审计报告仍依赖浏览器打印，不是原生报告包 |
| AI | 任意 OpenAI 兼容接口；规则识别 + LLM 复核补全；失败回退本地规则 | 无逐条证据引用、置信度、多模型共识、评测集 |
| 历史 | SQLite 持久化、版本 diff、重开复用 | 无实际值、无基线偏差、无生产率校准 |
| 协作 | 单机单用户；可导出/导入全量数据 | 无组织/团队、RBAC、SSO、评论、审批、签收 |
| 报表 | 首屏四图、结果页锚点、打印 PDF、CSV/MD | 无报告中心、无追溯矩阵、无签收页、无密级/水印 |
| 主题 | 浅色/深色/高对比；6 套品牌色 + 自定义；跟随系统 | 无主题工作室、无白标、无密度/字体设置、无插件主题 |
| 可访问性 | 键盘主流程、aria、焦点环、对比度按 WCAG 口径校验 | 目标可升级到 WCAG 2.2 AA 与 200% 缩放 |
| 性能 | 2000 条上限，全量重绘，不做虚拟滚动 | 10,000 条需要虚拟化与增量渲染 |
| 集成 | GitHub Issues 推送、CLI、本地 REST API | 无 Jira/ADO/GitLab/Feishu/OpenAPI/Webhook |
| 质量 | 18 个回归套件；金标准 US=105.07 | 新 UI/主题/报表需要新增视觉与报告快照测试 |

**结论：** 当前产品在“识别—复核—出表—留痕”主链路上明显强于所有直接同类；短板集中在**复核体验、审计交付、实际值闭环、企业协作、设计系统**，而不是基础计算。

### 4.1 七条竞品启示

1. **直接同类验证了“标准复杂度 + 离线 + 审计报告”是刚需，但没有一家做成文档自动化。** 应继续把识别与复核做深，而不是回头做基础计算器。
2. **企业采购的分水岭是审计与权限，不是计算。** StandardPoint 的 PDF 审计报告、SSO、备份，OpenProject 的组合/预算/RBAC，都是企业版的信号。
3. **估算信任来自闭环。** Epoch 的实际值、校准、蒙特卡洛说明：只给期望值不够，必须让用户看到“过去估得准不准、这次有多大把握”。
4. **协作不是聊天，而是角色化评审。** Thunderdome 的实时估算、OpenProject 的评审流，价值在“谁在什么依据下确认/驳回”，而不是消息数量。
5. **现代 UX 的核心是“视图 + 命令 + 证据 + 性能”。** Plane 的保存视图、命令式操作、分析面板，比换配色更能提升日常效率。
6. **主题应升级为品牌资产。** 企业要白标、报告抬头、安装器、登录页一致；只做暗色模式无法满足交付场景。
7. **AI 必须可审计。** fp-control 的一致性校验与稳定 ID 说明：AI 生成内容必须能回溯到原文、规则、模型与版本，否则不能进入正式造价。

### 4.2 建议的双轨策略

- **A 轨：单机离线版（默认）。** 保持零云依赖、文档不出本机、xlsx 母版保真；重点提升复核效率、报告质量、主题与性能。
- **B 轨：可选工作组版（私有化/局域网）。** 面向 5–20 人评估团队，提供共享项目库、RBAC、SSO、评论与签收、审计日志；仍不提供公网 SaaS，部署在客户内网。
- **共享底座：** 同一套 Python 引擎、同一套数据 schema、同一套前端设计系统；B 轨只增加服务端能力，不分裂产品。

## 五、优化需求清单

> 优先级定义：P0 = 3–6 个月内必须完成，直接影响采用与信任；P1 = 6–9 个月，形成差异化；P2 = 9–12 个月，面向规模化与生态。  
> 规模为相对工作量：S ≤ 1 人周，M = 2–3 人周，L = 4–6 人周，XL > 6 人周；仅用于排序，不是交付承诺。

### 5.1 客户体验提升（10 项）

| ID | 需求 | 现状/痛点 | 方案要点 | 验收标准 | 优先级/规模 |
|---|---|---|---|---|---|

## 六、P0 专项设计

### 6.1 复核工作台 2.0（CX-03 / UI-03 / UI-04）

**目标：** 把“逐条看表格”升级为“证据驱动决策”，让 100 条复核从耗时操作变成可度量流程。

**关键设计：**

- 左栏为模块/风险大纲，显示未复核、AI 低置信度、重复嫌疑、缺失数据功能的数量。
- 中栏为虚拟化表格，保留批量选择、排序、筛选、列预设、密度切换；首列冻结。
- 右栏为证据抽屉：原文段落高亮、规则命中、AI 建议与置信度、历史相似项、驳回原因。
- 底部粘性汇总：已确认/待确认/高风险、UFP/US/费用实时变化；主按钮“确认无误 → 生成结果”。
- 键盘：↑↓ 移动、Enter 确认、Space 查看证据、Ctrl+Z 撤销、Ctrl+K 命令面板。
- 自动保存与崩溃恢复；批量操作可撤销。

**验收：** 100 条复核用时下降 ≥30%；证据抽屉 ≤300ms；10,000 行滚动 60fps；键盘可完成全流程；三主题与中英文无破版。

**风险：** 三栏在 1024/768 下拥挤，需降级为“表格 + 抽屉”；虚拟化与批量编辑的状态同步复杂，需先做数据层抽象。

### 6.2 审计报告中心（FN-06 / UI-06）

**目标：** 把“浏览器打印”升级为“可交付、可签收、可追溯”的审计包，覆盖银行/国企/外包结算场景。

**报告结构：**

1. 封面：项目、客户、版本、密级、评估人/审核人、日期。
2. 执行摘要：规模、工作量、费用区间、关键假设、风险提示。
3. 方法与口径：IFPUG/NESMA/PERT 选择、复杂度矩阵、费率版本、调整因子。
4. 明细：功能 ID、类型、DET/RET/FTR、重用/修改、UFP/US、判定依据、原文位置。
5. 追溯矩阵：需求章节/段落 ↔ 功能项 ↔ 验收/用户故事。
6. 假设与变更：范围、费率、AI 模型/提示词版本、人工调整记录。
7. 签收页：评审意见、驳回原因、签收人/时间、版本哈希。

**验收：** 一键生成 PDF ≤30s；目录/页码/水印/密级正确；每个数值可回溯到原文与公式；报告模板可配置；中英文界面下交付物仍为中文。

**风险：** PDF 排版与 xlsx 母版是两套渲染链，需统一数据快照；密级/水印涉及权限，工作组版要先做 RBAC。

### 6.3 实际值闭环与概率预测（FN-03 / FN-04）

**目标：** 让估算从“一次性数字”变成“可校准的预测系统”，建立客户信任。

**关键设计：**

- 项目结项录入实际人天、起止日期、范围变更、偏差原因（需求/估算/资源/技术/外部）。
- 自动计算：偏差率、绝对偏差、MAPE、偏差方向（高估/低估）、按团队/领域/阶段分组。
- 校准：≥5 个项目后，给出生产率/调整因子建议；不自动篡改历史，只生成“建议系数”。
- 蒙特卡洛：任务级三点分布；支持依赖与资源约束；输出 P50/P80/P95、达标概率、关键风险 Top5、敏感性龙卷风图。
- 情景：乐观/基准/保守；可复制情景做“如果范围+10%、费率+5%、AI 提效 20%”对比。

**验收：** 200 个任务模拟 ≤2s；结果可复现；报告展示区间而非单点；实际值可导出；校准建议有样本量与解释。

**风险：** 实际值涉及绩效敏感，默认仅本人/项目可见；校准样本不足时不得给出“伪精确”系数。

### 6.4 稳定功能 ID 与增强基线（FN-02 / FN-01）

**目标：** 支撑“改造项目/二期/运维”场景，让功能点像需求资产一样可版本化。

**关键设计：**

- 每个功能项生成稳定 ID（如 `ILF-001`、`EI-007`），跨版本、跨导入导出保持不变。
- 增强项目加载基线：按 ID 匹配，自动分类 ADD/CHG/DEL/CFP；支持手工调整并留痕。
- 输出 EFP、更新后 UFP、变更明细；与现有版本 diff 打通。
- 标准 IFPUG 复杂度作为可选口径：DET/RET/FTR 矩阵；企业母版口径继续默认，报告注明口径。
- 基线文件可导出/导入，支持签名校验，防止篡改。

**验收：** 跨 3 个版本 ID 稳定；增强项目自动分类准确率 ≥90%（人工复核后 100%）；EFP 与手工计算一致；金标准不回归。

**风险：** 现有历史数据没有稳定 ID，需要迁移策略：首次打开时生成并写入，旧版本 diff 保持兼容。

### 6.5 设计系统与主题工作室（UI-05 / TH-01 / TH-02 / TH-03）

**目标：** 从“三套主题 + 品牌色”升级为“可治理、可白标、可扩展”的设计系统。

**关键设计：**

- Token 三层：原始（色阶/字阶/间距）、语义（surface/ink/brand/success/danger/warning）、组件（button/table/chart）。
- 主题 JSON：版本、名称、token 覆盖、图表色板、打印覆盖；导入导出；构建时校验硬编码。
- 主题工作室：实时预览、对比度检查、字体/密度/圆角/阴影、保存/分享。
- 白标品牌包：Logo、应用名、图标、登录/关于、报告抬头、安装器；按客户保存与回滚。
- 组件库：按钮、输入、选择、弹窗、抽屉、Toast、Tabs、Stepper、Table、Chart、空态/加载/错误；本地文档 + 视觉回归。
- 图表主题：色盲安全、线型/图案辅助、深浅背景自动切换。

**验收：** 新增一个品牌主题 ≤1 天且不改组件代码；对比度低于 4.5:1 阻断保存；UI/报告/安装器品牌一致；三主题 + 强制颜色视觉回归通过。

**风险：** 当前前端为原生 JS 单文件构建，组件库不能引入重框架；应以“轻量组件 + 设计令牌 + 构建脚本”实现，避免架构翻修。

| R2 | 6–12 周 | 复核与审计体验 | CX-03、UI-03、FN-06、CX-05、UI-07、CX-01、CX-02、CX-06、UI-01 | 100 条复核 -30%；审计包 ≤30s；WCAG 2.2 AA 0 阻断 |
| R3 | 3–5 个月 | 预测闭环 | FN-02、FN-03、FN-04、FN-01、FN-09、FN-10 | 稳定 ID；≥5 项目校准；P50/P80/P95；AI 评测 ≥85% |
| R4 | 5–8 个月 | 协作与集成 | FN-05、FN-08、FN-07（试点）、CX-07、UI-06、TH-02、TH-03、TH-04 | 工作组版可选启用；评审/签收闭环；3 个集成上线 |
| R5 | 8–12 个月 | 组合与生态 | FN-07、FN-11、FN-12、FN-13、CX-08、CX-09、CX-10、UI-02、TH-06 | 组合看板；插件 API；批处理；白标交付 |

**排序逻辑：**

1. 先修“每天都会用”的复核与性能，再做“评审会需要”的报告与演示。
2. 先做“可信”的稳定 ID、实际值、概率预测，再做“协同”的审批与组织。
3. 先做“可治理”的 token 与组件，再做“可售卖”的白标与插件。
4. 组合看板与商务报价放后，因为它们依赖稳定的项目数据与权限模型。

## 九、风险、边界与不做清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 范围蔓延到通用项目管理 | 资源分散，核心体验变差 | 明确不做聊天、CRM、完整甘特；组合看板仅做估算相关 |
| 多用户架构改造过大 | 破坏本地轻量优势 | 双轨：单机版不变；工作组版独立服务端，共享引擎与 schema |
| 历史数据迁移 | 旧项目打不开/ID 冲突 | schema 版本化；首次打开生成稳定 ID；双读兼容 |
| AI 幻觉与审计风险 | 正式造价不可信 | 证据引用、置信度、人工确认、评测集、模型版本入审计 |
| 10k 行性能 | 卡顿导致放弃 | 虚拟滚动、Worker、增量渲染、性能预算门禁 |
| 主题/组件重构 | UI 回归 | token 先行、组件逐个替换、视觉回归三主题 |
| 许可证污染 | 法律风险 | 只借鉴模式，不复制 GPL/AGPL 代码；依赖许可证审计 |
| 企业安全合规 | 无法入内网 | 工作组版支持 SSO/RBAC/审计日志/加密；默认本地 |
| 中英文案膨胀 | 漏翻/破版 | i18n key 对齐检查；伪本地化测试；截图回归 |
| 报告版式漂移 | 对客交付不专业 | 报告快照测试；xlsx 金标准；PDF 逐页目检 |

**明确不做（本阶段）：**

- 不做公网 SaaS、不做强制云同步。
- 不做全自动无审核出表。
- 不做通用 IM/CRM/完整项目管理。
- 不做移动端完整编辑（仅保留平板/窄屏只读与审批，若企业版验证需要）。
- 不做未经审计的 AI 自动确认。

## 十、结论与下一步

**结论：** 工作量评估助手的核心链路已经领先于 GitHub 上的直接同类；真正的差距不在“算功能点”，而在“让人更快地信、让团队更顺地评审、让企业更放心地交付”。下一阶段应坚持本地优先，围绕复核工作台、审计报告、实际值闭环、设计系统四条主线迭代；企业协作以可选工作组版推进，不牺牲单机体验。

**建议立即启动的三件事：**

1. **两周概念验证：** 复核工作台三栏 + 审计报告样张 + 主题工作室原型，找 3 位真实评估师试用。
2. **建立基线：** 记录首次估算时长、100 条复核时长、报告生成时长、10k 行性能；没有基线就无法证明优化。
3. **确认双轨边界：** 单机版与工作组版的功能边界、数据同步方式、许可与部署模型；先做架构决策，再排期。

**建议的 P0 开工顺序：**

1. UI-05 + TH-01：先把 token 与组件底座做稳，避免后续页面反复返工。
2. UI-04 + CX-04：数据网格与自动保存，直接改善每天的使用体验。
3. CX-03 + UI-03：复核工作台，拿下效率与证据链。
4. FN-06：审计报告中心，形成对客交付的差异化。
5. FN-02 + FN-03 + FN-04：稳定 ID、实际值、蒙特卡洛，建立预测信任闭环。
