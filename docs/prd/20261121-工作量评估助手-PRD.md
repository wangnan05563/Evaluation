## 1. 全面评审结论

### 1.1 评审方法

对 37 项需求逐项做五维评审：战略一致性、需求完整性、一致性与去重、可测试性、技术可行性、优先级与可排期性。同时检查与现有产品“不做全自动出表、不做云端同步、不做移动端适配、不做报价审批流转”的边界冲突。

### 1.2 评分

| 维度 | 评分 | 结论 |
|---|---|---|
| 战略一致性 | 8/10 | 本地优先、可审计、文档到造价的方向正确 |
| 需求完整性 | 7/10 | 功能覆盖好，但缺非功能、数据迁移、安全、AI 评测 |
| 一致性与去重 | 6/10 | 9 组需求存在重叠或依赖关系，需按 Epic 合并 |
| 可测试性 | 6/10 | 验收标准多为定性描述，需改为可执行断言 |
| 技术可行性 | 6/10 | PDF 引擎、工作组架构、原生 JS 设计系统存在未知 |
| 优先级合理性 | 5/10 | 14 个 P0 没有对应版本容量，单版本不可执行 |
| 可排期性 | 5/10 | 12 个月完成 37 项偏乐观，按 6–8 人团队需 18 个月 |
| 综合 | 6.5/10 | 方向可立项，但必须先收敛范围与决策 |

### 1.3 主要发现

1. **方向正确，但不能直接排期。** 37 项需求是“能力清单”，不是“版本计划”；必须按依赖与用户旅程切成可交付版本。
2. **颗粒度差异过大。** CX-06 是一个空态组件（S），FN-07 是组合管理（XL），不能放在同一优先级池里直接比较。
3. **存在 9 组重叠或强依赖。** 复核工作台、报告中心、设计系统、协作、组合、AI 质量、模板插件、主题品牌、上手导航都需要合并为 Epic。
4. **14 个 P0 超出单版本容量。** 需要把“优先级”和“版本”分开：P0 是 12 个月内必须完成，V1.1 只承载其中 10 项。
5. **缺少 12 项非功能要求。** 性能、可靠性、安全、隐私、兼容、无障碍、国际化、可观测、可维护、数据迁移、许可证、报告保真均未进入原需求。
6. **存在 4 处产品边界冲突。** 审批、移动端、云端、全自动出表与现有“不做清单”冲突，需用“可选工作组版”解决，而不是推翻单机定位。
7. **存在 5 个技术未知。** PDF 引擎、工作组数据库与认证、原生 JS 设计系统、蒙特卡洛性能、稳定 ID 迁移均需先做技术 Spike。
8. **验收标准不可直接测试。** “体验更好”“更专业”不是验收；必须写成给定条件、操作、预期结果。
9. **缺少交付治理。** 没有 RACI、回滚方案、试点用户、发布门槛与数据迁移演练。
10. **12 个月计划偏乐观。** 按 6–8 人团队，V1.1–V2.0 可在 12 个月内完成；V2.1 组合与生态建议放到 12–18 个月。

### 1.4 评审处置

| 评审问题 | 处置 | 结果 |
|---|---|---|
| 37 项颗粒度不一 | 合并为 15 个 Epic、45 个用户故事 | 可排期、可验收 |
| 9 组重叠 | 按用户旅程合并，保留原需求 ID 做追踪 | 不丢需求 |
| 14 个 P0 无版本 | 增加“优先级 × 版本”双轴 | V1.1 17 项、V1.2 9 项、V2.0 5 项、V2.1 6 项 |
| 缺非功能 | 新增 NFR-01–NFR-12 | 进入每个版本验收 |
| 4 处边界冲突 | 单机版保持不做；工作组版可选提供 | 不破坏本地优先 |
| 验收不可测 | 关键故事改为“给定/当/则” | 可直接写测试 |
| 缺技术验证 | 增加 5 个 Spike，放在 V1.1 前 4 周 | 降低返工 |
| 缺治理 | 增加 RACI、回滚、试点、发布门槛 | 可交付 |
| 12 个月偏乐观 | 调整为 18 个月全量，12 个月完成 V1.1–V2.0 | 计划可信 |

### 1.5 评审结论

**有条件通过。** 本 PRD 可作为 V1.1 细化与开发基线，但基线化前必须关闭 5 项决策：工作组版是否立项、PDF 引擎选型、标准 IFPUG 口径默认、稳定 ID 迁移策略、AI 数据边界。关闭后进入 V1.1 需求冻结。

## 2. 产品定义

### 2.1 背景与机会

当前产品已打通“需求文档 → IFPUG 候选 → 人工复核 → 成品 xlsx”的本地闭环，在直接同类中具备明显差异化。短板不在计算，而在复核效率、审计交付、实际值校准、企业协作与设计系统。GitHub 直接同类多为单机、手工、单点工具；成熟能力集中在项目组合、时间成本、实时协作与概率估算四个相邻赛道。

### 2.2 产品定位

**本地优先、可审计、从需求文档到企业造价表的工作量评估工作台。**

- 单机离线版：默认形态，数据不出本机，服务个人评估师与内网用户。
- 工作组版：可选局域网/私有化部署，服务 5–20 人评审团队，不做公网 SaaS。
- 两者共享同一引擎、数据格式与设计系统，不分裂产品。

### 2.3 产品目标

| 目标 | 指标 | 目标值 | 衡量方式 |
|---|---|---|---|
| G1 复核效率 | 100 条复核用时 | 下降 ≥30% | 用户测试 + 操作日志 |
| G2 审计交付 | 审计包生成时间 | ≤30 秒 | 任务计时 |
| G3 估算可信 | 项目 MAPE | ≤20%（≥5 个项目后） | 实际值闭环 |
| G4 体验一致 | 10k 行交互 p95 / 无障碍 | ≤150ms / WCAG 2.2 AA 0 阻断 | 性能埋点 + 审计 |
| G5 企业可扩展 | 工作组试点 / 集成 | 5–20 人试点；3 个集成上线 | 试点反馈 + 集成验收 |

### 2.4 非目标

- 不做公网 SaaS、不做强制云同步。
- 不做全自动无审核出表。
- 不做通用 IM、CRM、完整项目管理。
- 不做移动端完整编辑；仅支持 1024/768 与 200% 缩放，平板只读审批可选。
- 不做 AI 自动确认；所有 AI 建议必须人工复核。
- 不做发票开具、税务申报；仅做报价单/合同附件。

### 2.5 目标用户

| 角色 | 核心任务 | 主要痛点 | 成功标准 |
|---|---|---|---|
| 评估师 | 导入文档、复核候选、出表 | 表格密集、证据分散、重复劳动 | 5 分钟出初稿，100 条复核快 30% |
| 项目经理 / PMO | 组合排序、进度、实际值 | 看不到估算 vs 实际、缺产能 | 组合看板与偏差分析 |
| 财务 / 商务 | 费率、报价、审计 | Excel 版本多、口径难追溯 | 报价与估算同源，审计包可签 |
| 审核人 / 架构师 | 复核、驳回、签收 | 缺证据链、缺签收记录 | 逐条证据 + 签收页 |
| 管理员 | 安装、备份、升级、权限 | 缺健康检查、迁移风险 | 5 分钟体检，可回滚 |
| 外部客户 / 审计 | 只读报告 | 无脱敏分享、无密级 | 水印 PDF、只读链接 |

### 2.6 核心用户旅程

1. **首次评估：** 选择角色 → 导入样例/真实文档 → 识别候选 → 复核 → 生成结果 → 导出 xlsx。
2. **100 条复核：** 打开复核工作台 → 按风险排序 → 看证据 → 批量确认/驳回 → 查看汇总变化。
3. **审计交付：** 打开报告中心 → 选模板 → 预览 → 生成 PDF → 审核人签收 → 归档。
4. **结项校准：** 录入实际人天 → 查看偏差/MAPE → 生成校准建议 → 下个项目采用。
5. **二期改造：** 加载基线 → 按稳定 ID 分类 ADD/CHG/DEL/CFP → 输出 EFP → 报价。

### 2.7 产品原则

- 本地优先：默认不联网、不上传、不依赖 CDN。
- 人在回路：AI 只建议，不自动确认、不自动出表。
- 审计优先：每个数值可回溯到原文、规则、公式与版本。
- 渐进披露：默认简单，复杂能力按角色/场景展开。
- 不做框架翻修：在现有原生 JS + Python 架构上演进，避免大爆炸重写。

## 3. 版本范围

### 3.1 版本划分

| 版本 | 时间（T0=立项日） | 主题 | 包含需求 | 退出标准 |
|---|---|---|---|---|
| V1.1 | 0–4 个月 | 体验与审计版 | 17 项 | 复核 -30%；审计包 ≤30s；10k p95 ≤150ms；WCAG 2.2 AA 0 阻断 |
| V1.2 | 4–8 个月 | 预测闭环版 | 9 项 | 稳定 ID；EFP 一致；≥5 项目校准；P50/P80/P95；AI 评测 ≥85% |

| V2.1 | 12–18 个月 | 组合与生态版 | 6 项 | 100 项目 5s；费率卡；插件 API；100 文档批处理 |

### 3.2 V1.1 体验与审计版

**目标：** 让每天的使用更顺、让评审会能直接投屏、让审计能签字。

**范围：**

- 设计系统与三层 token；三主题/高对比/色盲；WCAG 2.2 AA。
- 10k 行虚拟化数据网格、列预设、密度、冻结首列、批量编辑、撤销。
- 自动保存、崩溃恢复、长任务进度/取消/续跑。
- 三栏证据复核工作台；风险大纲；证据抽屉；键盘操作。
- 报告中心、7 部分审计包、演示模式、脱敏分享。
- 角色化引导、命令面板、空态/错误态、应用壳与项目上下文。
- 性能预算与视觉回归。

**不包含：** 稳定 ID、实际值、蒙特卡洛、标准 IFPUG 复杂度、工作组、组合、费率卡。

### 3.3 V1.2 预测闭环版

**目标：** 让估算从“一个数”变成“有区间、有依据、可校准”的预测。

**范围：**

- 稳定功能 ID、增强项目基线、ADD/CHG/DEL/CFP、EFP/更新 UFP。
- 标准 IFPUG 复杂度可选模式；企业母版仍为默认。
- 实际值录入、偏差/MAPE、生产率校准。
- 蒙特卡洛、P50/P80/P95、达标概率、敏感性、情景对比。
- AI 证据/置信度、分歧清单、多模型共识、100+ 评测集、本地模型选项。
- 数据质量检查、主题工作室、密度/字体设置。

**不包含：** 工作组、审批、组合、费率卡、插件市场。

### 3.4 V2.0 企业协同版

**目标：** 让 5–20 人评审团队在内网协同，不牺牲单机体验。

**范围：**

- 可选工作组服务器、共享项目库、组织/用户/角色。
- RBAC、SSO、审计日志、备份/恢复/迁移/回滚。
- 项目状态机、评论/@/指派、签收页、通知/活动流。
- Jira/ADO/GitLab/GitHub/Feishu/OpenAPI/Webhook 集成。
- 白标品牌包。

**不包含：** 公网 SaaS、多租户计费、完整项目管理、移动端编辑。

### 3.5 V2.1 组合与生态版

**目标：** 让评估数据进入项目组合、商务报价与生态扩展。

**范围：**

- 组合看板、项目仪表盘、产能热力、甘特/关键路径（可选）。
- 多费率卡、多币种、税费/折扣、报价单/合同附件。
- 报表/主题模板、插件 API、自定义字段。
- 批处理、CI、失败队列、机器可读报告。

**不包含：** 发票开具、税务申报、插件市场分成。

### 3.6 假设与约束

- 团队假设：1 产品、2 前端、2 后端、1 测试、0.5 UX、0.5 AI，共 6–8 人；少于 5 人则时间顺延。
- 技术约束：现有 Python 本地引擎 + 原生 JS 单文件前端；不引入重型框架重写。
- 部署约束：默认 Windows 10/11 64 位离线；工作组版部署在客户内网。
- 数据约束：单机 SQLite；工作组版数据库选型在 V2.0 立项时决定。
- 合规约束：AI 默认不上传；客户数据不用于训练；许可证只借鉴模式，不复制 GPL/AGPL 代码。

## 4. 功能需求

### 4.1 E1 设计系统与无障碍基座

**目标：** 统一 token、组件、主题与无障碍，支撑后续所有页面。

**用户故事：**

- E1-S1 作为前端开发者，我希望颜色/字体/间距/圆角/阴影全部来自三层 token，以便新增主题不改组件代码。（TH-01）
- E1-S2 作为设计师，我希望有按钮/输入/选择/弹窗/抽屉/Toast/Tabs/Stepper/Table/Chart/空态组件及本地文档，以便新页面复用。（UI-05）
- E1-S3 作为色弱或键盘用户，我希望三主题、图表和全流程满足 WCAG 2.2 AA，以便无障碍完成评估。（UI-07、TH-05）

**验收标准：**

- 给定新增一个品牌主题，当只改主题 JSON 时，则 UI 与图表生效且组件代码零修改。
- 给定亮/暗/高对比/强制颜色四种状态，当检查文本与关键控件时，则对比度 ≥4.5:1，且无不可读文本。
- 给定键盘用户，当从导入到导出走完主流程时，则不使用鼠标也能完成，焦点不被遮挡。
- 给定 200% 缩放，当浏览主页面时，则无横向滚动（数据表格自身滚动除外）。

**优先级/版本/依赖：** P0 / V1.1；无前置依赖，但必须先于 E3/E4 页面开发。

### 4.2 E2 数据网格与编辑韧性

**目标：** 让大文档可用、编辑不丢、操作跟手。

**用户故事：**

- E2-S1 作为评估师，我希望 10,000 行表格虚拟滚动、排序/筛选/列预设/密度/冻结首列，以便大文档不卡。（UI-04）
- E2-S2 作为评估师，我希望编辑 1 秒自动保存、20 步撤销/重做、崩溃恢复，以便不丢数据。（CX-04）
- E2-S3 作为用户，我希望首屏 ≤2 秒、交互 p95 ≤150ms、主题切换 ≤300ms，以便操作跟手。（UI-08）

**验收标准：**

- 给定 10,000 行、8 列数据，当连续滚动 60 秒时，则帧率 ≥60fps，无白屏。
- 给定排序/筛选操作，当测量 p95 时，则 ≤150ms。
- 给定编辑后 1 秒内异常退出，当重开应用时，则恢复到最后一次编辑，丢失 ≤1 秒。
- 给定连续 20 次编辑，当点击撤销时，则逐步回退且不破坏公式/格式。

**优先级/版本/依赖：** P0 / V1.1；依赖 E1 的表格组件与 token。

### 4.3 E3 证据复核工作台

**目标：** 把逐条看表格升级为证据驱动决策。

**用户故事：**

- E3-S1 作为评估师，我希望左大纲/中表格/右证据三栏，以便边看原文边判定。（UI-03）
- E3-S2 作为评估师，我希望点击行看到原文、规则、AI 建议、置信度、历史先例，以便快速确认/驳回。（CX-03）
- E3-S3 作为评估师，我希望长任务显示阶段/剩余时间、可取消、可续跑，以便失败不重来。（CX-05）

**验收标准：**

- 给定 100 条待复核，当完成复核时，则总用时比现状下降 ≥30%。
- 给定点击任一行，当打开证据抽屉时，则 ≤300ms 展示原文、规则、AI 建议、置信度。
- 给定 10 分钟识别任务，当点击取消时，则 2 秒内停止；重开后可从未完成阶段续跑。

### 6.5 响应式与可访问性

- 断点：1440 三栏；1024 两栏；768/375 单栏 + 抽屉；表格自身横向滚动。
- 200% 缩放：主页面无横向滚动；数据表格可横向滚动。
- 键盘：Tab 顺序合理；焦点环可见；Esc 关闭；Enter 确认；Ctrl/Cmd+K 命令。
- 屏幕阅读器：表格有表头/行号/状态；图表有文字摘要；抽屉有标题与焦点锁定。
- 减少动态：尊重 `prefers-reduced-motion`；动画 ≤200ms。
- 颜色：状态不只靠颜色，配文字/图标/图案。

### 6.6 文案与国际化

- 中英文 key 100% 对齐；新增文案必须同时提交两种语言。
- 错误文案包含：发生了什么、影响、下一步动作、错误码。
- 术语统一：功能点、功能项、候选、复核、基线、审计包、工作台。
- 日期/数字/货币/百分比本地化；表格数字等宽。

## 7. 数据、报告与 AI

### 7.1 核心数据模型

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Organization | id、name、plan、settings | 工作组版可选 |
| User/Role | id、org_id、role、status | RBAC |
| Project | id、name、client、method、status、owner | 项目上下文 |
| Baseline | id、project_id、version、hash、items | 基线快照 |
| FunctionItem | stable_id、type、name、det/ret/ftr、complexity、reuse、modify、evidence_id | 稳定 ID 核心 |
| Evidence | doc_id、paragraph_id、quote、rule_id、confidence、model_version | 可追溯 |
| ReviewDecision | item_id、user、decision、reason、time | 复核留痕 |
| Estimate | method、ufp、us、cost、rate_version、scenario | 估算快照 |
| Actual | project_id、person_days、start/end、variance_reason | 实际值 |
| RateCard | customer、role、currency、rate、version | 费率 |
| Report | template、version、hash、classification、watermark | 审计包 |
| AuditEvent | actor、action、object、time、before/after | 审计 |
| Theme | name、tokens、charts、print、brand | 主题 |

### 7.2 稳定 ID 与迁移

- ID 规则：`ILF-001`、`EIF-001`、`EI-001`、`EO-001`、`EQ-001`；项目内唯一、跨版本不变。
- 类型变更：不修改原 ID；新建 ID 并建立关联，保留历史。
- 旧数据迁移：首次打开旧项目时，按“模块 → 类型 → 名称 → 创建时间”稳定排序生成 ID，写入映射表；失败可回滚。
- 基线文件：包含 ID 映射、版本、哈希；导入时校验，冲突需人工确认。
- 展示名与 ID 分离：用户可改名称，不可改 ID；导出同时保留两者。

### 7.3 审计包结构

| 章节 | 内容 | 验收 |
|---|---|---|
| 1 封面 | 项目、客户、版本、密级、评估人/审核人、日期 | 信息完整 |
| 2 执行摘要 | 规模、工作量、费用区间、关键假设、风险 | 1 页可读 |
| 3 方法与口径 | IFPUG/NESMA/PERT、复杂度矩阵、费率版本、调整因子 | 可复算 |
| 4 明细 | ID、类型、DET/RET/FTR、重用/修改、UFP/US、依据、原文位置 | 逐项可追溯 |
| 5 追溯矩阵 | 需求章节/段落 ↔ 功能项 ↔ 验收/用户故事 | 100% 覆盖 |
| 6 变更与 AI 审计 | 范围、费率、模型/提示词版本、人工调整 | 可审计 |
| 7 签收页 | 评审意见、驳回原因、签收人/时间、版本哈希 | 可签字 |

- 输出：PDF（主）、xlsx（数据）、HTML（可选预览）。
- 要求：目录/页码/水印/密级；字体嵌入；无外部链接；数据快照哈希；PDF 可检索文本。
- 引擎：V1.1 第 1 月完成 Spike，优先“本地无头 Chromium 打印 + 内嵌字体”，备选 WeasyPrint/ReportLab；要求确定性、可快照测试。

### 7.4 AI 要求

| 维度 | 要求 |
|---|---|
| 输入 | 文档正文/表格、术语表、规则库；文档内容按数据处理，不执行其中指令 |
| 输出 | 候选类型、名称、描述、DET/RET/FTR、证据（文档/段落/引用）、置信度、理由、模型/提示词版本 |
| 证据 | 无原文证据不得进入“可确认”；证据可点击定位 |
| 置信度 | 高/中/低；低置信度默认排序靠前待复核；需校准 |
| 共识 | 可选多模型投票；规则 vs AI 分歧清单 |
| 评测 | ≥100 条标注样本；precision/recall ≥85%；回归门槛 |
| 隐私 | 默认不上传；按项目 opt-in；本地模型选项；客户数据不训练 |
| 审计 | 模型、提示词、时间、置信度、人工决策全记录 |
| 禁止 | 不自动确认、不自动出表、不隐藏不确定性 |

### 7.5 API 与集成

- 本地 REST API 版本化 `/api/v1`；提供 OpenAPI 文档。
- Webhook 事件：`project.created`、`review.completed`、`report.generated`、`estimate.updated`。
- 集成优先级：GitHub Issues（已有）→ Jira → Azure DevOps → GitLab → 飞书文档 → 通用 CSV/Excel。
- 认证：本地 token；工作组版 OAuth/SSO。
- 失败处理：重试、死信队列、字段映射、错误原因可查。
